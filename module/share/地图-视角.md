# SunsetLinux 视角地图（Root 部署）

> **先读这一页，再动手。** 这台机器上同一个路径字符串在不同"视角"下指向**不同的目录**，
> 拿绝对路径去猜"工作区在哪"必然翻车（本项目的 AI 会话就差点踩）。
>
> 想看你**此刻**在哪个视角：`linuxctl whereami`（动态版；`--json` 给工具用）。
> 本文件是静态版，随模块发布。

---

## 1. 三个视角（真机实测，OnePlus PJD110 / Android 16）

| 视角 | 你在哪 | 看到的 `/data/sunsetlinux` | 挂载命名空间（实测） |
|---|---|---|---|
| **MT 管理器 / 全局** | Android 真机根 | **真的那棵**（含 `upper.img`、`dirs-upper`、`bin`） | `mnt:[4026532884]`（pid 1） |
| **设备 shell**（ksu su） | Android 真机根，但另一个 ns | 同一棵树，**看不到环境私有挂载**（`upper/` 是空挂载点） | `mnt:[4026536055]` |
| **环境内部**（本容器） | overlay 合成视图 | **看不见 `/data`**（没有这个路径） | `mnt:[4026535677]` |
| **某个 proot 容器**（如 DSHA 的 Ubuntu） | 它自己的 rootfs | ⚠️ **影子目录**：`/data` 没被 bind 进来时会解析到 rootfs 里的 `data/`，是**另一份**（inode 都不一样） | 随容器而定 |

> 实测证据：同一个 f2fs 分区（device `65103`）上，真目录 inode `1652135`，
> 影子目录 inode `2909534` —— **同名不同物**。只看路径永远分辨不出来 ⇒ 先 `whereami`。

## 2. 路径地图（环境内部 ↔ 宿主）

| 环境内部看到 | 宿主（MT）上是 | 说明 |
|---|---|---|
| `/` | `/data/sunsetlinux/rootfs` | overlay **合成视图**：base+runtime+dsh 三层 erofs 只读 + 可写层 |
| 你写的任何文件 | `/data/sunsetlinux/upper/upper/…` | **可写层**（`upper.img` 里的 `upper/` 目录）。双 `upper` = 镜像挂载点 + upperdir 目录名，不是 bug |
| `/mnt/sdcard` | `/storage/emulated/0` | Android 共享存储（`/storage/emulated/0` 是指向它的软链）。**Download 就在这里** |
| `/share` | `/data/sunsetlinux/share` | **交换目录**（本文所在处）：两侧同一批 inode，0777 |
| `/run` | `/data/sunsetlinux/run` | 状态/日志（`state.json`、`dsh.url`、`linux.log`…），两侧同一批文件 |

overlay 的真实入参（环境启动日志里那行）：
`lowerdir=…/layers-mnt/{dsh,runtime,base},upperdir=/data/sunsetlinux/upper/upper,workdir=/data/sunsetlinux/upper/work`

## 3. 怎么和宿主交换文件（按推荐度）

1. **`/share`（最省事）**：容器里丢进 `/share`，宿主侧就是 `/data/sunsetlinux/share`（MT 直接进这个目录）；
   反过来宿主丢进去，容器里 `/share` 立刻可见。**不需要 root，不需要碰 upper。**
2. **`/mnt/sdcard/Download`**：走 Android 共享存储。适合"从手机里拿文件"。
3. 直接写可写层（`/data/sunsetlinux/upper/upper/…`）：**能用但脆**——只有能看见那个挂载的
   命名空间才有这个路径，而且 uid/gid、SELinux 上下文要自己摆平。非必要不用。

## 4. 环境内 DSH 的权限模型

- **默认 `danger-full-access`**（无沙箱、不弹审批）：环境本来就是"真 chroot + 真 root"
  （uid 0、SELinux 域 `u:r:ksu:s0`），而 DSH 的沙箱在这台机器上**没有可用后端**
  （无 `bwrap`、Landlock 未暴露）——`workspace-write` 只会 fail-closed 把命令拒掉，
  逐条提权没有任何收益。
- 想改回去：在 `$DSH_HOME/env`（默认 `/root/.dsh/env`，0600）里写
  `DSH_PERMISSION_MODE=workspace-write`（或 `read-only`），**重启环境**后生效。
- 实现是**一条变量**（DSH 组合原文）：
  `policy: (DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'`。
  审批功能没有被删——不设它时策略就是 `workspace-write` + `ask`。

## 5. 已知坑（都踩过）

- **`/data/...` 在 proot 容器里可能是假的**：先 `linuxctl whereami`，看 `view` 是不是 `shadow`。
- **环境私有挂载只有环境自己看得见**：宿主 shell 里 `upper/` 往往是空挂载点，这不代表环境没在跑。
- **不要用 `ls /data/sunsetlinux/upper/upper` 判断环境状态**：状态看 `linuxctl status` 或
  `/data/sunsetlinux/run/state.json`。
